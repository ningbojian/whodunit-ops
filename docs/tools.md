## 1. 文本抽取

`app/tools/extract.py` · ✅ 已实现 · 只读

把社群 / 朋友圈口语化拼场文案、玩家预约 / 跳车消息，一次转成 `sessions` 与 `bookings` 两组结构化记录。

- **只读文本，不写库。** 输出交给工具 2 去重、工具 6 落盘。`candidate_session_id` 只是「门店 + 剧本 + 时间」算出的**候选**，本工具不查场次表，也不调用 `upsert_booking` / `cancel_booking`。
- **输出契约**：场次记录包含落盘字段（门店、剧本、类型、开场时间、总位、原价、状态、原文）与审计字段。原文里的「已约 N 人」「还差 N 人」只以 `remaining_reported` / `booked_reported` 回显，**永不落盘**——人数真相只能来自预约明细；`start_time_text`、`start_time_source`、`source_excerpt`、`notes` 同样只供店长核对，不进入 Excel。`sessions_frame()` 只保留落盘字段，可直接喂 `dedupe_sessions()`。
- **时间以原文确定性解析优先。** 模型同时输出原文时间短语与绝对时间；代码先验证短语确实出现在原文里，再按确定性规则解析完整日期、月日 / 号 + 时刻；解析不了才采用模型推断值，并写入「时间由模型推断」备注。原文时间允许 `[now-7 天, now+370 天]`，模型推断收紧到 `[now-1 天, now+180 天]`；两者不一致时以原文为准并标注。「今晚 / 明晚 / 周六 / 下周六」属于模型推断范围，不假装是代码算出来的。
- **失败与降级分开。** 空输入、缺 API key、模型调用异常、坏 JSON、顶层结构错误都返回结构化失败（`ok=false` + `error_code` + `error` + `raw_snippet`），不向调用方抛异常；单条记录不是对象则跳过并警告；单个字段坏则降级为 `null` + `notes`，整批仍然成功。坏 JSON **不自动修复**，否则模型输出质量下降会被悄悄掩盖。
- **防幻觉是缓解，不是消除。** Prompt 要求原文没有的值一律 `null`、原文只当数据不当指令；代码再校验时间短语、`source_excerpt`、门店 / 剧本是否逐字出现。**店长仍是第一道校验人。**
- **已知边界**：只支持文本、不做 OCR、不接微信；不做全角 / 别名 / 模糊匹配；超长文本不分块；单条消息里的多场 / 多玩家依赖模型正确拆分。

**运行方式**：`scripts/07_extract_demo.py` 默认使用脚本内 FakeLLM，离线、不需要 API key；`--live` 才调用真实 DeepSeek。`tests/test_extract.py` 通过 autouse fixture 阻止任何测试意外初始化真实模型。

## 2. 场次去重

`app/tools/dedupe.py` · ✅ 已实现 · 只读

识别商家重复转发的同一条拼场信息。同一场次的定义是 **门店 + 剧本 + 开场时间**（归一化到分钟）——三个维度都相同才是同一场，19:30 和 21:30 是两车。

- **合并以字段为单位，不以行为单位。** 同一场转发三次：先发完整海报（8 人本、168 元、情感本），几小时后发「还差 2 人」，改价后再发「今晚特价 158」。按整行去重会只剩最后一条残缺记录；本工具逐字段合并，**最后一个非空值胜出，空值永不覆盖**，结果是 `8 人本 / 情感本 / 158`。这同时修掉了跨批次写入时 `NA` 抹掉旧值的同类缺陷。
- **两个非空值冲突时取后者**（改房、改价都会重发，后发的更接近当前状态），但字段名会写进 `conflict_fields` 对调用方可见。`source_text` 刻意排除在冲突报告外——同一场转发三次原文必然三份不同，算进去会让报告永远非空。
- **身份缺失不静默撞键，也不让整批崩掉。** 门店 / 剧本 / 开场时间缺失或无法解析时，坏行**不参与合并、原样放行**，原因写入 `dedupe_note`（`门店缺失` / `剧本缺失` / `开场时间缺失` / `开场时间无法解析`）。旧实现会把 `str(pd.NA) == "<NA>"` 当身份参与哈希，所有缺门店的行撞成同一场；`pd.NaT.strftime()` 则直接抛异常，让整批写入崩溃。身份判定必须在类型整形之前完成——整形会把「无法解析」静默变成 `NaT`，之后就分不清了。
- **显式 `session_id` 是调用方的逃生舱。** 场次表**没有房间字段**，同店 + 同剧本 + 同时间完全可能是两个房间同时开。调用方给出两个不同的显式 ID 时，工具不合并，只标注 `联合键相同但session_id不同`；**显式 ID 与联合键算出的值不一致时，保留显式值并标注**。
- **输出四种动作**：`更新` / `无变化` / `新增` / `未比对`。`changed_fields` 只统计「传入值非空且与旧值不同」的字段；`booked_seats`、`status` 永不参与比对，因为 storage 落盘时会无条件保留它们。分析列 `dedupe_action` / `merged_count` / `conflict_fields` / `changed_fields` / `dedupe_note` **永不落盘**。
- **全项目只有一份合并规则**：策略语义在工具 2，物理实现在 `storage.py`，`upsert_sessions` 复用同一份代码，两边不会漂移。错误策略刻意不对称：分析层放行并标注，落盘层对算不出主键的行抛 `ValueError`——主键为空的行一旦进 Excel，身份就永久丢失。

本工具**没有需要标定的阈值**：「同一场次」是定义，不是经验参数。**名称只做 `strip`，不做全角 / 半角、别名或模糊匹配**——`年轮` 与 `年轮（情感本）` 是两个剧本，不会被合并。已知边界：区分不了同店同剧本同时间的两间房（靠显式 ID）；已有重复数据不会被清理，本工具是写前分析层，不是表清洗器。

## 4. 空场风险识别

`app/tools/risk.py` · ✅ 已实现 · 只读

输出**两个互相独立的维度**：

| 维度 | 取值 | 回答的问题 | 用途 |
|---|---|---|---|
| `fail_risk` | 高 / 中 / 低 | 这场**会不会黄** | 预警：要不要提前通知客人、准备流局 |
| `priority_level` | 高危 / 关注 / 正常 | 现在**该先动手救哪场** | 派活：朋友圈与折扣投给谁 |

两者方向经常**相反**：缺口大 = 情况糟（更容易黄），同时缺口大 = 难救（更不值得动手）。同一个变量回答两个方向相反的问题，因此不能只算一个「危险度」——只按危险度排序会把救不回来的场次排在最前、推一把就锁定的排在最后，方向是反的（**上一版实现正是这么排的**，现已改为下面的两维口径）。

- **核心量是需要的到客速率** = 剩余空位 ÷ 剩余小时（人/小时），再除以门店常态到客速率得到倍数。它把人数与时间放进同一尺度，且天然是绝对人数口径（房间大小不影响找人难度）。
- **优先级 = 紧迫档 × 可救性档**（≤2h / ≤6h / 其余 × 倍数 ≤1 / ≤2 / >2）。两档**相乘**——只有「快开场了 + 还救得回来」才判高危，相加或取 max 会把「已经没救」和「还早得很」都误判成该动手。
- **排序只按 `priority_level`**；救不回来的场次**不丢弃**，仍留在结果里（带着 `fail_risk = 高`），可按该列单独筛出「该考虑流局的场次」。**规模（总位）单独一列，不计入打分，只作排序的第二个关键字。**
- 已满员（含超额预约）的场次所有档位归零，直接判正常。等级**不落盘**，每次读取时重算，因此空位填满后高危标记会自行消失；已开场与已取消的场次由工具 3 在函数内部自动剔除，调用方不必记得先调工具 3。

⚠️ **阈值目前为占位值，未经任何真实门店数据标定。** 模型结构（时间越少越紧迫、需要的人比平时来的多就越难救、满员无风险）可论证，具体数值只能由门店标定。其中 `normal_arrival_rate` 影响最大——**谁比谁优先直接取决于它**，见 [参数标定](tuning.md)。

## 5. 动态折扣定价

`app/tools/pricing.py` · ✅ 已实现 · 只读

回答「这场该让多少、让到哪条线为止」。复用工具 4 的 `rate_multiple`，按倍数分四档给出对外推荐售价：原价 / 轻让 95% / 中让 88% / 重让 80%。

- **折扣只作用于剩余空位**（限时特价），已预约的客人仍按原价结算。设已约 `b` 人、原价 `p₀`、每人变动成本 `v`、降价后多来 `k` 人，差额是 `k·(p − v)`——**只要售价高于 `v`，每多来一个人都是净赚的，与降了多少无关**。所以折扣力度不影响「划不划算」，只影响「能拉来几个人」；后者取决于价格弹性，门店没有这个数据。因此档位是经验值，模型算的是让利的经济账，不声称算出了最优价格。
- **两条保本线，不能混用**：

| 字段 | 含义 | 性质 |
|---|---|---|
| `floor_price` | 每人变动成本 | **边际底价，硬约束**。低于它，多卖一个位子多亏一笔。与人数、原价都无关 |
| `break_even_price` | 固定成本 ÷ 到客人数 + 变动成本 | **均摊保本价，不能当售卖下限**。它回答的是「这个价卖满，这场赚不赚」。到客越少，每人分摊的固定成本越高，它越高——10 人本到客 2 人时可达 260 元，高于原价 |

- 最有行动含义的一列是 `contribution_per_seat` = 推荐价 − 变动成本，即「每多来一个客人，这场少亏多少钱」。

⚠️ **与工具 4 的结论经常相反，这是刻意的。** 工具 4 的 `rescue_level = 0`（倍数 > 2）意思是**填不满**，判「正常，别浪费推广力气」；工具 5 问的是**能不能少亏**，填不满不等于不该少亏。所以倍数 4.0 的场次在工具 4 里是「正常」、在工具 5 里是「重让 80%」。反过来，工具 4 判「高危」的场次（倍数 ≤ 1）恰恰**不需要**打折——自然流量就够。一句话：**要推广 ≠ 要让利**。折扣的触发条件是倍数 > 1，不是 `rescue_level == 1`。

- **底价外泄防护做成结构而非约定**：内部财务列登记在 `INTERNAL_COLUMNS`，下游通过 `public_view()` 取数，拿到的 DataFrame 里根本没有这些列。注意 `contribution_per_seat` **不在**这份名单里（它仍是成本推导值），工具 7 另有一层 `COPY_FIELDS` 白名单。

⚠️ **成本与折扣参数目前为占位值，未经任何真实门店数据标定。** 已知偏差：`contribution_per_seat` 是上界（一部分降价买家本会按原价购买，这部分损失未计入）；单场视角，不处理同一晚多场折扣互相抢客；总位是时长的代理指标（12 人机制本与 12 人欢乐本时长可能差一倍，成本却算成一样）。

## 6. 表格存储与读取

`app/tools/storage.py` · ✅ 已实现 · 读写

采用双表模型。**场次表**记录有哪些场、什么时间、几位、多少钱；**预约明细表**记录谁约了哪一场。玩家预约 / 跳车消息输入后自动更新空位。

已约人数由预约明细汇总得出，同一玩家同一场次重复预约不会重复计数，避免消息被转发两次就多算一人。存储通过 `Store` 接口与业务逻辑解耦：CLI 与导入导出使用 `ExcelStore`；Web 数据库模式在本地（无 `DATABASE_URL`）使用 `SqlStore`（SQLite），生产使用 `SqlStore`（Neon Postgres）。三种后端共用同一套合并规则，写入语义均由整表替换保证。

## 7. 营销文案生成

`app/tools/copywriter.py` · ✅ 已实现 · 只读

读取实时场次数据，内部完成选场，生成**社群短版**与**朋友圈配图长版**两套文案。只读数据、不写库、不自动发布，店长人工复核后复制发布。

- **输入与选场**：直接接收 `storage.load_sessions_with_counts()` 的场次表，内部调用工具 4 / 5 取得优先级与推荐价，**不要求调用方先定价**。选场采用逐级回退：高危 → 关注 → 正常可推广场次；高危不足时用关注补，关注不足再用正常补满名额，低级别绝不排到高危前面。**已满员、已开场、已取消、缺少门店 / 剧本 / 开场时间或剩余空位的场次被排除**，并给出跳过说明。默认最多 3 场，硬上限 5 场。
- **一次只写一个门店**：一条文案混两家门店会让玩家不知道去哪。未指定 `store_name` 且可推广场次跨多个门店时返回 `bad_request`，要求调用方指定门店；**指定后只取该门店**。
- **两层脱敏，不靠注释提醒**：工具 5 的 `public_view()` 会剔除 `floor_price` / `break_even_price` / `sunk_cost` / `profit_if_sold_out`，但**保留 `contribution_per_seat`**——它同样是成本推导值。因此工具 7 在 `public_view()` 之后再加一层 `COPY_FIELDS` 白名单：只有门店、剧本、类型、开场时间、总位、已约、剩余、原价、推荐价、省下金额能进入 Prompt 和结果；风险等级、`contribution_per_seat`、`source_text`、内部财务列都不会出现。白名单是「按名单保留」，将来工具 5 新增列默认进不了 Prompt。
- **生成后两道整次失败**：提示词要求不写内部财务概念、不编造价格与折扣，但提示词不是保证。代码在生成后再查两件事：出现「保本 / 底价 / 成本 / 利润 / 内部价 / 进价」或内部列名 → `internal_leak`；出现数据里没有的价格数字、把省下金额当售价、或「X 折」等未授权折扣 → `price_mismatch`。两种情况下 `community` 与 `moments` **同时置空**，不返回半套文案——有字就可能被店长直接复制。
- **失败码**：空表 / 全部不可推广 → `no_sessions`；参数或表结构错误 → `bad_request`；缺 API key → `config_error`；模型初始化 / 调用异常 → `model_init_error` / `llm_call_error`（**错误信息脱敏**）；坏 JSON / 顶层非对象 → `bad_json` / `bad_root`；两版文案缺失或为空 → `bad_copy`。业务失败都返回结构化 `CopyResult`，不向 ReAct 循环抛异常；`KeyboardInterrupt` / `SystemExit` 原样抛出。
- **已知边界**：文案质量、语气、长度由模型决定，代码只校验结构、内部词和价格；内部词是保守关键词匹配，可能误杀「低成本快乐」这类普通表达；价格校验只覆盖常见数字写法，中文数字、模糊价格、半价 / 买一送一无法完全识别；选场只按风险优先级，不做同晚多场互相抢客或利润全局优化；不做玩家直连、不自动发送微信、不自动发布。

**运行方式**：`scripts/08_copywriter_demo.py` 默认使用脚本内 FakeLLM，离线、不需要 API key；加 `--live` 才调用真实 DeepSeek，且只打印「检测到 DEEPSEEK_API_KEY：是/否」，不打印 key 的值。`tests/test_copywriter.py` 覆盖选场回退、双层白名单、`internal_leak` / `price_mismatch`、配置与模型异常、坏 JSON 等场景，全部离线。

## 8. 剧本库与缩写别名

`app/tools/scripts.py` · `app/tools/public_library.py` · ✅ 已实现 · 读写（公共库只读）

把「剧本本身的信息」从场次表里独立出来。场次回答什么时候开、谁约了；剧本库回答全名、别名 / 缩写、类型、几人本、时长、参考原价和备注。数据在 `data/scripts.xlsx`（私有库），网页版每个邮箱各有一份；另有全店共享的**公共剧本库**（`data/public_scripts.xlsx` / `public_scripts` 表）。

- **允许残缺，先存后补**：只要店长给出全名或至少一个别名，`upsert` 就会先落一条档案，并返回 `profile_status`（`待确认名称` / `待补全` / `已完整`）、`missing_fields` 与 `next_question`。必填字段是全名、类型、适合人数、时长；别名、参考价、备注可选。下一轮带上返回的 `script_id` 继续补，空值不会覆盖已有值，已保存的字段不会被重复追问。人数 / 时长 / 价格接受 `8人`、`4小时`、`168元` 这类写法并做范围校验；无法识别的值进入 `invalid_fields`，不会为了凑完整而编造。
- **缩写怎么处理**：`search` 合并三类本地来源——私有剧本库的 `script_name` / `aliases`、公共剧本库（只读，`pub-` 前缀 id），以及 `sessions.xlsx` 里出现过的剧本名。场次历史只读，不会自动写回剧本库。匹配只做空白折叠、大小写归一和包含匹配，**不做拼音匹配**；一条都没命中、或只命中 `loose`（查询里恰好夹着某个短剧名）时才走兜底：先查全局剧名记忆，再给字符 bigram 近似候选（最多 3 条，要求与查询至少共享 2 个 bigram 且重叠系数 ≥ 0.5，标 `suggested`；已经出现在结果里的短名不参与候选打分，否则它们恒为 1.0 的重叠会占满这 3 个名额；查询短于 3 字直接返回空，因为《青搂》与《青楼》的 bigram 零交集，硬猜只会给出假候选）。每条结果都带 `match_quality`——`exact` / `prefix` / `partial` / `loose` 是正常匹配的强弱，`learned` 来自全局剧名记忆，`suggested` 是按字面相近猜的候选，`list` 是空查询的列表输出；模型据此决定是否要先请店长确认全名。本地查不到时，Agent 可以根据自己的知识提出「我猜是《…》」并等店长确认，也可以走工具 12 `web_search` 查公开信息（标注「网络信息非官方」）；**工具 8 本身不联网、不猜名字，也不会把模型候选静默写入档案。** 缩写识别率取决于本地档案、公开搜索命中与模型知识，**不能保证正确**——本地查不到时 Agent 只能给出带「猜」标记的候选，必须由店长确认全名。
- **共享剧名记忆（`remember`）**：`script_library(action="remember", query=店长最初的说法, script_id=…)` 把一条「说法 → 公共库条目」的映射写进全局表 `script_aliases`（Excel 模式是 `data/script_aliases.json`）。**只在店长确认全名之后**调用，且只对公共库条目有效；存的是归一化后的剧名，不含对话正文、报价、排期或客户信息。写入前有一道 store 层校验，过不了直接拒绝：

  | 错误码 | 什么时候 |
  |---|---|
  | `sensitive_query` | 含联系方式、链接，含不可见字符（控制符 / 零宽 / 双向覆盖 / 孤立代理对 / 组合字素连接符 / 变体选择符 / 韩文填充符 / 盲文空白，以及 Unicode 名称里含 FILLER、BLANK、REPLACEMENT 的各文字空位填充符），或**目标剧名里没有数字而说法里混入了数字**（`青楼138`） |
  | `not_similar` | 拼写离目标名太远；或数字对得上但数字前后的符号、单位对不上（`￥1440`、`14:40`、`8月16` 都不是《1440》/《8/16》的写法）；或编号本身对不上（`16号` 挂不到《8/16》） |
  | `collides_with_other` | 这个说法已经是另一个公共剧本的剧名 |
  | `ambiguous_query` | 这个说法**同时像**好几个剧名（系列本、只差一个字的两本）；只对 3 字及以上的说法判定 |
  | `redundant` | 说法就是剧名本身 |
  | `script_not_public` | 目标不是当前公共库里的条目 |
  | `alias_quota_exceeded` | 全局表或这个剧本的说法数到上限 |

  判据分三段，都是**从结构上**限制这张表能表达什么，而不是靠关键词：长度 ≥4 的键必须对齐到目标名的某一段连续子串（长度差 ≤1、编辑距离 ≤1）；长度 2–3 的键必须是原名里**逐字连续**的一段，不许带错字（短键带一个错字等于「三个字里两个能凑」，「老板说」这类对话就会被当成剧名）；目标名本身 2–3 字时，规则换成「等长且至多改一个字」，否则《青楼》的两字错拼永远进不来。数字按 Unicode 的 N 类逐个比对（`①` 也是数字），目标名没有数字而键有、或数字串对不上都拒绝——`16号` 不能挂到《8/16》上。**数字对得上之后还要比对数字之外的骨架**：目标名是纯数字时键也只能是数字；目标的骨架里只有 `/` `%` 这类分隔符时要求逐字相同；其余情况按名字对齐规则比。没有这一层，`￥1440`、`14:40` 的数字串都是 1440，会被当成《1440》的另一种写法写进全局表——报价和场次时间就是这么进来的。歧义判定用的是同一套判据：只要这个键也够格当**另一个**公共剧名的写法，就不记。同一条键再次被确认时，若原目标已随公共库重导消失，这条映射会改指向这次确认的目标（原目标仍在则保持先写者胜）——否则一次合法确认会被回成「此前已有记录」，而库里仍指着一个不存在的本。

  代价是离原名太远的口语说法学不进去，这是有意的 fail-closed。冲突先写者胜，已存在时只返回通用的「已收录」，不告诉调用方是谁先写的。读取**只在正常匹配为空（或只剩 `loose` 弱匹配）时**点查一次，无缓存，且**不参与打分**——学到的键若并进别名列表，就能在 `(score, name_len, name_key)` 排序里顶掉真正的精确命中。`loose` 行把结果名额占满时照样会查（那种场合最需要兜底），学到的命中排在 `loose` 行前面：它是整串查询的精确键，比「查询里夹着个短名」强。

  **生效范围只在检索**：`script_library(search)` / `get` 会查这张表；建场（`create_session`）的剧本匹配走另一套包含匹配，**不查全局记忆**——建场会把匹配到的名字写成场次的正式剧名，用一条本店没核对过的全局映射静默改名，比搜不到更糟。打错的名字会原样落成剧本名，需要时直接改场次字段。
- **公共库只读、私有遮蔽**：`upsert` 永远只写私有库；`pub-` 开头的 id 传入 upsert 直接拒绝（`public_readonly`）。同名（`name_key`）时私有行遮蔽公共行，**私有条目优先生效并有 warning 提示**。**场次永不指向公共行**：命中公共库时预填类型 / 人数 / 价格，但不写 `script_id`，结果标 `script_source=公共库`。
- **数据与边界**：列包括 `script_id`（全名哈希或 `draft-xxxxxxxx`，公共行为 `pub-` 前缀）、`script_name`、`aliases`（`/`、逗号、分号分隔）、`script_type`、`total_seats`、`duration_minutes`、`list_price`、`notes`、`source_text`、`created_at`、`updated_at`（公共行另有 `origin` 来源标注与 `imported_at`）。剧本库只描述剧本，不承担排期；具体场次仍由工具 6 写入。当前没有独立的剧本库管理页面，入口是 Agent 工具；不做图片 / OCR。

**测试**：`tests/test_scripts.py`、`tests/test_public_library.py`、`tests/test_script_aliases.py` 与 `tests/test_agent.py::TestScriptTool`。

## 10. 资源排期

`app/tools/scheduling.py` · `app/tools/assignment.py` · ✅ 已实现 · 读写

在场次时间固定的前提下，为每场分配一个房间和一个主 DM。

| 约束类型 | 内容 |
|---|---|
| 硬约束 | 房间启用与容量；DM 启用 / 技能 / 班次 / 每日上限；房间与 DM 占用区间不重叠；翻台与休息缓冲 |
| 目标 | 先最大化可安排场次数，再最大化预计贡献 |

小规模用分支限界求到最优；超过节点上限时如实返回 `optimal=false`，**不把有界搜索结果说成最优**。

- **只分配，不改场**：不修改 `sessions.start_time`，不自动合并、取消或候补场次；已有手工 assignment 默认锁定，不被静默覆盖。
- 排不开时返回原因码（容量、技能、班次、资源重叠等）和最多 3 条建议（换房、换 DM、改期、取消 / 候补、补资源）。只有换房 / 换 DM 会在店长选择后写库；改期 / 取消只给确认文案，不自动执行。
- 收益估值使用默认上座率假设，只作内部参考，不进入营销文案。

排期在 Web / App 侧的使用见 [资源排期与看板](scheduling.md)。

## 12. 联网搜索 web_search

`app/integrations/web_search.py` · ✅ 已实现 · 只读（不写库）

本地剧本库未命中时查询公开网络信息（发行信息 / 类型 / 测评动态）。可插拔 Provider（默认 Tavily，密钥只放本地 `.env` / Render Secret，由使用者自行填写）。**未配置 `WEB_SEARCH_API_KEY` 时工具恒注册但返回 `not_configured`**，提示改用本地剧本库——不因缺 key 报错，也不伪装有结果。

**三道服务端硬闸门**（在调用 Provider 之前执行，被拒请求零成本）：

1. **入参校验**——长度 2–120 字、拒绝名单（天气 / 股票 / 时政 / 明星等无关话题）、正向信号要求（剧本域关键词 / 《》书名号 / 「XX剧本杀」形态），不满足即 `query_rejected`。
2. **租户日配额**——`WEB_SEARCH_TENANT_DAILY_LIMIT`（默认 10，夹取 0–100）。
3. **全局日配额**——`WEB_SEARCH_GLOBAL_DAILY_LIMIT`（默认 30，夹取 0–500）。

默认 30 次/天 × 30 天 ≈ 900 ≤ Tavily Free 档 1,000 credits/月，结构上不触发付费超量（2026-10-22 从 tavily.com/pricing 核实）。计数落 `search_usage_daily` 表（Excel 模式 JSON sidecar），仅在 Provider 调用成功后递增；失败 / 缓存命中不计数。

**结果使用边界**：最多 3 条，必须标注「网络信息非官方」并附来源链接；**绝不根据搜索结果自动写入剧本库**——需店长确认全名后走 `script_library(upsert)`；禁查玩家隐私、商家后台、微信内容。查询放行 / 拒绝写一行不含 PII 的审计日志（query 截断 40 字），key 永不入日志。

**测试**：`tests/test_web_search.py`（全部 mock，不产生真实调用）。
