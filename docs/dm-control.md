# DM 场控与 Flutter 双角色端

实现见 `app/tools/dm_control.py`、`app/tools/stages.py`、`app/web/dm.py`；Flutter 源码在 `mobile_app/`。

---

## 阶段模板

商家在 Web `/stages` 从剧本库已有剧本创建阶段模板，填写阶段名、时长、提前提醒、DM 提示 `cue_text`、到点文案 `prompt_text` 和可选硬件场景 JSON。

保存时校验序号连续、时长与提醒范围、JSON 结构；模板版本加一。场控启动时把当前 active 阶段快照进 run，**运行中修改模板不影响本场**，下一场才使用新版本。

## 场控状态机

`pending → active ⇄ paused → completed`，另有 `abandoned`。

| 角色 | 能做什么 |
|---|---|
| 商家 | 对已有场次生成一次性 8 位场控码（默认 30 分钟、单次使用、库中只存 HMAC）；撤销令牌；查看只读直播。**不能远程推进、暂停或结束** |
| DM | 兑换场控码得到 run-scoped Bearer token（默认 12 小时）；开始场控、暂停 / 继续、上一幕 / 下一幕、延长 1–20 分钟、结束（二次确认） |

兑换后仍是 `pending`，DM 点「开始场控」才进入第一幕计时。最后一幕点「下一幕」返回 `at_last_stage`，**不会自动结束**。

**DM 最小权限**：场控码一次性、默认 30 分钟有效，库中只存 HMAC；DM token 只绑定单个 run，默认 12 小时，**不能访问商家 API，也不能列出其他场次**。越权 `run_id` 统一返回 404，不泄露该 run 是否存在。

**结束后的基础汇总已实现**：`dm_control(action="report")` 与 Web `/api/runs/{run_id}/report`，包含各阶段计划 / 实际停留、超时、暂停、硬件失败次数。

## 倒计时只提醒，绝不推进

服务端没有 cron、后台线程或 `asyncio.sleep` 推进阶段，`stage_ends_at` 只用于展示和客户端提醒。

DM 端到点只发本地通知、标红「已超时」并显示超时秒数，**不调用 `next`**。测试会把时间冻结并推过 `stage_ends_at`，断言阶段、版本和事件数都不变。App 被杀后重开，用服务端时间戳重建剩余时间，不续跑本地倒计时。

## 硬件增值模式

默认纯软件模式，只推送文字提示。每场可单独切换硬件模式；切换阶段时先提交阶段状态与事件，再调用通用 HTTP `HardwareAdapter` 下发灯光 / 音效场景。

硬件超时、连接失败或非 2xx 时，阶段**不回滚、不阻塞**，run 标记 `hardware_degraded`，后续降级为文字提示并记录 `hardware_failed` 事件，DM 可手动「重试硬件」。离线补传的动作不补发硬件指令。

`HARDWARE_SKILL_URL` / `HARDWARE_SKILL_TOKEN` 只来自服务端环境变量；未配置时硬件模式返回 `hardware_not_configured`。

> 这是**通用 HTTP 适配器契约**，**未对接任何具体灯光 / 音效厂商**。真实地址、鉴权与场景字段需要拿到厂商协议后再联调。

## 断线与并发

每个动作带客户端生成的 `client_event_id` 和 `expected_version`；重复事件幂等，版本冲突返回 `stale_state` 与当前 run，客户端以服务端状态重同步。

断网时 DM 端把动作写入本地队列（上限 200 条），恢复后按序补传；补传不发送硬件。同一场次最多一个未结束 run，同一 DM 最多一个进行中 run。

## Flutter 双角色客户端

`mobile_app/` 是同一套 Flutter 工程。

| 端 | 能力 |
|---|---|
| 商家端 | 邮箱申请 / 轮询、Agent 对话（含操作按钮）、排期（紧凑列表 / 时间轴双视图 + 场次详情页）、快速占位、点评文件导入、生成场控码、只读场控 |
| DM 端 | 只读本场排期 / 房间 / 阶段模板，负责计时和手动推进；**不能**创建场次、剧本或资源 |

token 存 `flutter_secure_storage`，不写日志或 URL；离线队列只存动作与版本，不存玩家信息。

**不做微信小程序**：Flutter 不能直接编译为小程序，单独维护第二套 UI 的成本不在本轮范围；Web 兜底页仍可在微信内打开。

验证状态（已通过什么、还没做什么）见 [验证记录](verification.md#flutter-客户端)。

## 对话操作按钮

`/api/app/chat` 与 `/api/chat` 响应在助手回合附带 `choices`（服务端从工具结果白名单提取，≤8 个按钮、label ≤40 字、payload 只含 JSON 标量，绝不拷贝裸信封字段）。只有两类按钮：

- **快捷追问**（`quick_reply`）：payload 只含预填文本，点击即重发一条消息，不提交任何写。建场结果 `needs_confirmation` 时，剧本候选拆成最多 5 个「就开《XX》」按钮，点选即重发文本让 Agent 重新建场。
- **冲突解决**（`resolve`）：仅 `switch_room` / `switch_dm` / `keep_unassigned`。Flutter 端直连业务 API（`/api/app/schedule/resolve`，Bearer 鉴权），不经模型；回执以系统气泡展示，不伪造成功文案。

**Web 端诚实降级**：`/api/app/*` 需要 Bearer token，Cookie 会话不可达——浏览器里 quick_reply 可用（重发文本），业务按钮渲染为「（请在 App 内操作）」文本，不新增 web 专属写端点。

## 排期双密度（Flutter）

App 排期页默认紧凑单行（时间 + 剧名 + 座位/状态点，无房间/DM/价格），AppBar 菜单可切时间轴（10:00–次日 04:00 视窗、跨午夜映射、越界 clamp 并标记）；点场次进详情页（全字段只读 + 生成场控码 + 换房/换 DM）。

密度偏好存 `SharedPreferences`（key `schedule_density`）。时间轴换算为纯函数（`schedule_timeline.dart`），已单测覆盖。

**移动端不做拖拽看板**：触屏拖拽在小屏的误触成本高，改期属于低频管理动作，下一轮再评估。

## 双端分工

| 端 | 定位 | 理由 |
|---|---|---|
| **Web** | 配置与管理端：资源建档（房间 / DM / 班次 / 请假）、剧本库筛选分页、排期看板（时间拖拽 + 状态转换）、CSV 导入、阶段模板、审批与访问管理 | 桌面大屏，操作密集型任务都在这里 |
| **Flutter** | 现场与响应端：店长移动端查看排期 / 快速占位 / 对话操作按钮 / 生成场控码；DM 端场控计时与手动推进 | 场控发生在房间现场，DM 手不能离开手机；断线离线队列保证房间内弱网可用 |

**chat choices 为什么 App 优先**：操作按钮直连业务 API（Bearer token），Web 端 `/api/app/*` 是 Cookie 不可达的，诚实降级为「（请在 App 内操作）」文本 + quick_reply 重发文本，不为按钮另开 web 写端点。

## 商业模式参考（方向探讨，非承诺）

本产品定位是**门店私域运营辅助工具**，与轻兔、谋杀之谜秘书等店务 SaaS 互补而非替代——对方管支付、收银、C 端售票履约，本产品管「场次能不能开起来」这一段：拼场进度、DM 排班与带本评级、剧本库事实元数据、场控复盘、只读经营报表。

**明确不做**：储值 / 支付 / 订单履约、C 端售票、微信自动触达（风控）。

引流钩子的思路：DM 端必须用手机 → 场控码兑换即「体验入口」→ DM 熟悉产品后反向推动门店采购 Web 端；离线可用是现场刚需卖点。

**竞品功能参考**：基于行业公开资料的归纳，本环境未能实时联网核实，仅作方向参考。常见商家版功能簇里与本项目契合、值得后续借鉴的：DM 出勤 / 值班表（本项目已有班次 + 请假，可扩展出勤统计）、场次复盘（已有场控事件流）、剧本销量 / 上座率排行（需先积累场次数据）、店员绩效提成（依赖出勤与带本记录，数据基础已具备）。不契合的：支付分账、C 端拼车小程序、库存进销存。
