# 资源排期、看板与渠道单

Web 侧对应页面：`/resources`、`/schedule`、`/imports`、`/stages`、`/runs`。Flutter 侧差异见 [DM 场控与双角色端](dm-control.md)。

---

## 资源与排期

场次录入**默认不填房间 / DM**：店长只填剧本、开场时间，人数与价格可后补；房间与 DM 由建场后的自动分配决定，也可在建场卡片里手动指定（失败不回滚场次，返回警告并保留自动分配结果）。

- 没有资源时返回 `resources_not_configured`，**不阻塞录入**。
- 发生冲突时场次照常保存，返回换房、换 DM、改期、取消 / 候补、先不排等选项，店长选择后才写排期。
- 排期只写 `session_assignments`，**不改开场时间、不合并、不取消场次**。

自动分配使用固定场次的约束搜索：房间容量、DM 技能与班次、每日上限、翻台与休息缓冲、已有手工分配锁定。小规模求到最优；触发搜索节点上限时返回 `optimal=false` 和 `search_truncated`，**页面与 Agent 都不能把它说成「最优」**。收益估值按当前预约与默认上座率估算，只供内部排序，不是收入承诺。

实现见 `app/tools/scheduling.py`、`app/tools/assignment.py` 和 `app/web/operations.py`。

## 建场逻辑（没有草稿）

Agent 对话的 `store_data(create_session)` 与 Web 的 `POST /api/sessions`、App 的 `POST /api/app/sessions`（平铺字段或 `{"fields": {...}}` 包装）共用 `app/tools/session_intake.py`。

硬必填只有「剧本全名」和「开场时间」；两项齐全就直接建场并自动排期（`status=promoted`，触发 `auto_assign`），人数、价格、类型、时长能从剧本库推断就推断，推断不到也不阻塞。

| 情况 | 行为 |
|---|---|
| 缺任意一项硬必填 | 只在对话里追问最关键的一项，**不落任何数据**；Web / App 返回 400 `incomplete_session` + 追问文案 |
| 剧本名命中多个候选 | 停在 `needs_confirmation`（同样不落数据），由店长点选候选（「就开《XX》」重发文本按钮）或补全信息后再建 |
| 唯一候选 | 自动确认并回显规范全名 |
| 指定了 `room_id` / `dm_id` | 先按原逻辑建场并自动分配，再用手工指定覆盖；覆盖失败**不回滚场次**、也不吞错误，返回 `manual_assign.status="failed"` 与「已建场，但手动指定未生效：…；已保留自动分配结果」 |

`room_id` / `dm_id` 在 Web 与 App 建场时是**可选**字段；Agent 对话工具仍不接受这两个字段。

已保存场次只改人数 / 价格 / 类型时原地更新，不换 `session_id`；改门店、剧本或开场时间会重算 `session_id`，并在同一个写锁内搬移预约、assignment、渠道单引用和已结束的场控历史。目标 ID 已存在返回 `duplicate_session`，新容量小于已约人数返回 `capacity_exceeded`；该场有 `pending/active/paused` 场控时返回 `run_active`，禁止改场次身份，也不留下半套数据。

## 排期数据基础

`/api/schedule` 与 `/api/app/schedule` 的场次载荷补 `duration_minutes`（剧本库时长，缺省 240），Flutter 时间轴直接吃到真实时长，不再 fallback 45 分钟。

手工改期（PATCH `/api/sessions/{id}`）在写入前做**分配撞档预检**：本场手工分配的房间 / DM 与他人区间（房间含翻台缓冲、DM 含 30 分钟休息缓冲）重叠则拒绝并返回对方 session_id 明细；带 `__force__` 才放行（仅 Web 看板二次确认后发送）——人确认 = 显式动作。

## 时间看板

> 本节的时间 / 状态看板、剧本筛选分页、DM 请假与带本档案、对话剧本名快速通道，均于 **2026-10-24** 上线。

Web `/schedule`（✅ 已实现；Flutter 未实现）。客户端从 `/api/schedule` 构建 06:00–26:00 业务轴日历板，Pointer Events 手写拖拽（鼠标 6px 阈值 / 触屏 250ms 长按、15 分钟吸附、克隆卡跟随）；drop 走 PATCH 乐观更新，失败回弹原位；id 重命名事件委托自动生效。

冲突 chips 直接复用 `build_schedule` 的建议结构：换房 / 换 DM 点击即调既有 resolve 端点，改时间建议需二次确认后走同一条 PATCH，加资源类只读。

**系统绝不自动改开场时间或取消场次**——每个 chips 动作都是人点击触发的显式动作。拖拽无 JS 测试设施，靠手动冒烟清单（CSP 下 CSSOM 写位置已在本地冒烟验证无拦截）。

## 状态看板

同页 tab 切换（✅ 已实现）：待开场 / 已开场 / 已取消三列，与时间看板共用一次 fetch。

拖拽换列走 `PATCH /api/sessions/{id}` 改 status（确认框注明「场控计时与剧情推进仍归 DM 端控制」），状态值只接受三态之一；已取消→已开场等非法转换前端直接拦截。

## 快速建场卡片

`/schedule` 看板置顶（✅ 已实现，2026-10-25 改为卡片）。「新增场次」按钮和点击时间看板空位都会弹出**建场卡片**（原生 `<dialog>`，自动带上点击处的日期与 15 分钟吸附时间）：

- 日期 / 小时 / 分钟按钮点选；
- 剧本搜索 + **类型下拉 + 人数筛选**（全部 / 4–9 人及以上）；
- 可选房间与 DM（首项「自动分配（推荐）」）；
- 人数与价格收在「更多信息」。

提交走 `POST /api/sessions`，成功后**不整页刷新**，只关闭卡片、弹 toast、重拉一次 `/api/schedule?include_scripts=0` 原地重绘两块看板。缺硬必填时服务端返回 400 `incomplete_session` + 追问文案，卡片原地显示，不落任何数据（没有草稿）。

场次 ID 由「门店 + 剧本 + 开场时间」决定，同一剧本同一时间再提交一次是**合并更新而不是新增**，这时提示会明确写「已合并更新，没有新建」，避免店长以为多了一场。

## 不整页刷新

排期页不再有 `location.reload()`。建场、应用分配、手工调整成功后统一走一次 `GET /api/schedule?include_scripts=0` 并**原地重绘**时间看板与状态看板；单调 token 丢弃乱序返回的旧响应，旧看板在新数据到达前保持可见。

`include_scripts=0` 让看板刷新不再序列化 5800+ 行公共剧本库（时长映射仍在服务端算好随场次下发）。这是「一次请求 + 重绘」，不是零延迟；拖拽改期仍走原有的单卡增量更新。

## 排期变更先审后写

「补齐未分配」与「生成优化方案」都是 **预览 → 逐条勾选（默认全选）→ 批量应用**。

- 预览接口（`POST /api/schedule/auto-assign` 默认 `preview:true`；`POST /api/schedule/plan`）只计算不写库，返回统一的 `proposals`：每行带 `session_id`、剧本名、开场时间、`before`（原房间/DM）、`after`（建议房间/DM）、`changed`、`source`。
- 应用走 `POST /api/schedule/apply`（必须 `confirm:true`），提交的是**用户看到并勾选的那几行**，服务端**不重跑求解器**，因此不会出现「看的是一套、写的是另一套」。服务端在同一个 `store_lock` 里重新校验房间容量、房间 / DM 时段重叠后**一次性写入，全有或全无**；任一行失败则一条都不写。
- 每行还带 `expect_room_id` / `expect_dm_id`（键存在即比对，空串表示「当时确实没有」）：期间被他人改过则返回 409 `preview_stale`，一条都不写，提示重新生成预览。
- 只缺房间或只缺 DM 的场次，`补齐未分配` 不动它（不冒险移动已有资源），而是在预览里单列 `partial` 并提示用「生成优化方案」；完全没分配的场次仍由 `补齐未分配` 处理。
- 已取消场次不占资源：求解器、预检与应用三处口径一致，避免「预览说可写、应用报冲突」。
- 所有写入都不碰 `start_time`、不改 `status`——**系统仍然绝不自动改开场时间或取消场次**。

**已知取舍**：

- 「补齐未分配」只处理完全没有任何分配的场次；优化方案不会移动已完整分配的场次（`lock_existing=True`）。
- 预览精度取决于预览那一刻的数据，人在预览与点击之间改动资源时会出现 `preview_stale`——这是预期行为，不是故障。
- **`apply` 的重新校验只覆盖房间容量与房间 / DM 时段重叠。** `expect_room_id` / `expect_dm_id` 能挡住房间或 DM 被换掉，但**挡不住「DM 班次被改」**——**DM 班次覆盖只在预览 / 求解时校验，apply 不重算班次**。预览后把某位 DM 的班次删掉或改短，这次写入依然会成功。要补这一步需要把班次校验搬进 apply（或在 `expect_*` 之外再加一种基线），属于行为变更，本轮未做。

## 资源模板中文表头

资源页下载的三个 CSV 模板是中文表头：

| 模板 | 表头 |
|---|---|
| 房间 | `房间编号,房间名称,可容纳人数,标签,每小时成本,缓冲分钟,是否启用,备注` |
| DM | `DM编号,DM名称,擅长类型,每小时成本,每日最多场次,是否启用,备注` |
| 班次 | `DM名称,星期,上班时间,下班时间` |

导入器把表头归一化（忽略大小写、空格、下划线、连字符）后**同时接受中文与旧英文表头**，导出 sidecar `rooms.xlsx` / `dms.xlsx` 仍可回导；缺必需列时提前返回 400 `missing_columns` 并给出中文指引。

## 渠道单

`/imports` 提供快速 +N 占位与大众点评导出文件导入（CSV/XLSX）。

- **快速占位**走 `/imports` 与 `/api/bookings/quick`，每次生成 `client_ref`，落一条可追溯的预约记录，默认玩家名为 `散客-xxxx`；服务端用确定性 `booking_id` 去重，重复点击不会重复占座；容量检查与写入在同一个写锁内完成，满员返回 `capacity_exceeded`。
- **减位仍走取消预约流程**，不提供直接改空位数字的按钮，避免绕过预约明细造成超售。
- **点评导入**先预览映射、前 10 行脱敏数据、未匹配场次与超容量场次，确认后才写入；按订单号幂等，重复导入返回 `unchanged`，退款 / 取消同步取消对应预约，某场超容量则整组拒绝该场，其他场正常导入。

**系统内部不会超售**；外部渠道仍存在时间差：只有订单导出并导入后，系统才看见这些座位，两次导入之间点评端仍可能接单。界面持续显示 `data_as_of`，超过 2 小时提示数据已过期，**不承诺实时同步**。

实现见 `app/tools/intake.py`、`app/integrations/booking_source.py` 与 `app/web/imports.py`。

## 剧本筛选分页

资源页新端点 `GET /api/scripts`（名称 / 别名包含、类型、人数区间、时长区间、来源 私有 / 公共库），`page_size` 夹取 10–200 默认 50；pandas 向量化过滤 5800+ 公共行毫秒级，不缓存。

首屏服务端渲染第一页（无 JS 可读），筛选交互由 app.js 增强；来源列公开展示「公共库」badge，公共库对商家只读。`/api/app/resources`（Flutter 契约）冻结不动。

## DM 档案

Web 优先，agent / Flutter 本轮不加写入口。

- 新表 `dm_leaves`（请假，Excel 后端 sidecar `dm_leaves.xlsx`，按 dm_id+日期幂等）。
- 带本历史从 `dm_runs ⋈ sessions` 自动派生（已取消场次不计），无需手动录入；`resources()` 与 `/api/schedule` 的 dms[] 附加 `leaves` / `past_runs` / `distinct_scripts` / `recent_scripts`（`script_counts` 只留在服务端排期用，不进载荷）。
- 排期集成两个可选 kwarg：
  - **请假 DM 当天不参与自动分配**（按落地业务日过滤，跨夜场次归开场那天）；
  - **熟悉度只作同收益时的次级排序键**（排在经济贡献之后，不翻盘最优性），选中 DM 没带过该本则 warning「DM X 没带过《Y》，请注意」。
- Web DM 卡可增删请假、展开带本记录。

## 对话剧本名快速通道

候选唯一时（别名或全名只命中 1 部）自动确认，回复追加「唯一匹配自动确认，请核对剧本全名《…》」并回显绝对日期时间；≥2 个候选仍出选择按钮。

**唯一匹配存在误建风险，靠「warning 回显 + 撤销」两层兜底**：店长说「撤销」→ Agent 调 `cancel_session`（只改 status=已取消，不删数据；缺确认拒绝、只读模式拒绝）。

## 页面与安全

所有非 GET 请求走 CSRF；页面保持无内联脚本、无内联样式、无外部 CDN；上传上限默认 2 MB，普通请求仍是 32 KB。Web 是桌面后台与兜底，不注册 service worker、不缓存登录态页面。

浏览器验收矩阵见 [验证记录](verification.md)。
